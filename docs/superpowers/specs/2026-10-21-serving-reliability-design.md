## 목적과 첫 검증 범위

사용자와의 프로젝트 논의에서 합의한 목적은 Kubernetes 기반 LLM 서빙의 운영 문제를 재현하고 디버깅하여, 개선 효과를 검증하고 필요할 때 오픈소스 기여로 연결하는 것이다.

첫 문제는 서버 scale-in 또는 배포 교체 중 진행 중인 스트리밍 요청이 어떤 조건에서 중단되는지 확인하는 것이다. CRD 구현 자체보다 재현 가능한 실험, 원인 분석, 개선 전후 증거가 성과다.

- 측정: 요청 중단율, 완료율, 종료 소요 시간, 응답 지연.
- 원인 분석: 클라이언트 요청 기록, 서버의 요청 처리·종료 로그, Kubernetes 리소스 상태 변화의 시간적 관계.
- 특정 추론 엔진의 결함이나 성능 개선을 사전에 가정하지 않는다. 설정만으로 해결되는 결과도 유효하다.
- 향후 활용: 오픈소스 이슈·수정 검증, 버전 업그레이드 회귀 검증, 운영 설정 비교, 기술 포트폴리오.
- 첫 완성 기준: 다른 사람이 제공된 구성과 절차로 스트리밍 중 종료·교체 실험을 재현하고 요청 결과와 종료 타임라인을 확인할 수 있다.

## 설계 방향과 책임

아래는 구현 예정 설계이며 API 이름·필드·상태 스키마는 아직 확정되지 않았다.

### ModelServing

- 모델, 실행 이미지, 자원 요구량, 배포·확장·종료 설정을 표현한다.
- Serving Reconciler가 Deployment·Service를 관리한다. 필요하면 메트릭 수집 설정과 KEDA 연계를 추가한다.
- 준비 상태와 엔드포인트를 제공한다.

### ExperimentRun

- 기존 ModelServing을 참조하고 부하 조건, 종료·교체 시나리오, 관측 조건, 성공 기준을 표현한다.
- Experiment Reconciler가 부하 발생 Job과 실험용 설정을 관리한다.
- 대상 준비 확인 → 부하 시작 → 요청 처리 중임을 확인 → 종료·교체 유발 → 결과 수집·판정 순서를 조율한다.
- 참조하는 서버를 소유하지 않는다. 실험 삭제가 기존 서버 삭제로 이어지면 안 된다.
- 서빙 Deployment를 직접 수정하지 않는다. 서빙 설정 변경은 ModelServing의 명시적인 인터페이스를 통해 요청한다. 자동 확장과 수동 조작의 충돌 정책은 구현 전에 정한다.
- 한 CR을 한 번의 실행으로 취급한다. 재조정이나 Controller 재시작으로 완료된 실험을 다시 실행하지 않는다. 재실험은 새 CR로 수행한다.
- 실험 실행 완료와 검증 기준 통과를 구분한다.

두 Reconciler는 초기에는 하나의 Operator 프로세스에서 실행한다. 같은 하위 리소스의 필드를 여러 Controller가 경쟁적으로 관리하지 않도록 한다.

### 관측과 결과

- 지표·로그 수집과 결과 저장은 공용 인프라로 구성한다. 실험마다 전체 관측 스택을 만들지 않는다.
- 실험은 대상, 시간 구간, 수집 지표, 결과 분석 조건을 관리한다.
- 클라이언트 기록: 요청 ID, 시작·첫 토큰 시각, 정상 완료 여부, 연결 오류.
- 서버 기록: 요청 처리 시작·완료, 종료 신호 수신, 종료 시 처리 중인 요청.
- Kubernetes 기록: Pod 삭제, readiness·EndpointSlice 변화, 컨테이너 종료 시각·이유.
- 요청 ID, Pod UID, 실험 ID, 시각을 연결할 수 있도록 한다. 요청 ID는 Prometheus 라벨에 넣지 않고 로그 또는 트레이스에 기록한다.
- 원본 데이터는 CR status 외부에 저장한다. status에는 진행 상태, 판정, 요약, 결과 위치를 남긴다.
- 재현을 위해 이미지 버전, 모델, GPU 종류, 서버 설정, 부하 조건을 결과에 기록한다.
