# 개발 작업 흐름

## 설계에서 머지까지

1. 브레인스토밍으로 문제와 범위, 접근 방식, 중요한 제약을 정리한다.
2. 설계를 리뷰하여 모순, 누락, 실패 상황, 미결정 사항을 확인한다.
3. 독립적으로 리뷰·검증·머지할 수 있는 PR 단위로 분할한다. 각 PR의 범위, 의존 관계, 검증 기준을 명확히 한다.
4. PR을 하나씩 구현하고 필요한 테스트와 코드 리뷰를 수행한 뒤 머지한다. 머지는 해당 세션에서 부여된 권한 범위 내에서 수행한다.
5. 머지된 결과를 기준으로 영향받는 위키를 갱신한다. 다음 PR이 해당 지식에 의존하면 먼저 갱신한다.

설계·계획·조사·실험 근거 문서는 `docs/` 아래에 보관한다. 세부 목차나 분량, 작성 도구는 강제하지 않는다. 기존 문서를 형식 통일만을 위해 다시 작성하지 않는다.

## 작업 중 참고할 정보

현재 PR의 설계·계획 → 관련 위키 섹션 → 실제 코드·테스트 순으로 필요한 맥락을 확보한다. 위키가 아직 없으면 관련 `docs/` 문서를 직접 참조한다. 과거 설계는 결정 이유를 추가로 확인해야 할 때만 읽는다.

현재 PR의 설계는 변경 목표이고 위키는 기존 상태를 설명할 수 있다. 둘의 차이가 의도한 변경인지 확인한다. 계획을 구현 완료나 검증 결과로 취급하지 않는다.

## 위키 갱신

- 갱신할 때 대상 근거 문서를 하나씩 명시하고 OpenWiki의 기존 스킬·도구를 사용한다.
- 입력 문서 하나가 출력 페이지 하나를 의미하지 않는다. 관련 코드·테스트와 기존 위키를 확인하고 영향받는 페이지에만 반영한다.
- 책임, 관계, 제약, 중요한 선택 이유, 검증된 동작과 한계를 남긴다. 논의 전체와 작업 목록을 복제하지 않는다.
- 기존 기준 페이지에 통합하고 다른 페이지는 요약과 링크로 연결한다. 이미 반영된 정보라면 변경하지 않는다.
- 원본 설계·계획은 작업 기록으로 보존한다. 설계 변경과 실제 구현의 차이를 구분한다.
- README는 위키 갱신의 입력 근거에서 제외한다. README 갱신은 아래의 별도 근거 범위를 따른다.
- 실제 위키 생성·갱신 완료 여부를 도구 결과로 확인한다. 수동 문서 이동을 OpenWiki 갱신 완료로 보고하지 않는다.

## README 갱신

- README는 AGENTS.md와 관련 하네스·위키 문서를 지식 베이스로 삼는다. AGENTS.md에 없는 내용도 관련 하네스·위키에 있으면 참고한다. 모든 문서를 일괄 읽지는 않는다.
- `docs/`는 설계·구현 및 위키 갱신의 근거 자료이며 README의 직접 입력이 아니다. 정보가 관련 하네스 또는 위키에 정리되기 전에는 README에 반영하지 않는다.
- AGENTS나 하네스에 docs 링크만 추가하는 것은 정보 반영이 아니다. 제품 지식은 위키에, 작업 절차는 하네스에 정리한다. README를 채우기 위해 제품 설계를 하네스에 복사하지 않는다.
- 허용된 근거가 없는 기존 README 내용은 근거 문서에 보존된 것을 확인한 뒤 README에서 제외한다. 위키가 없다는 이유로 docs를 직접 근거로 사용하는 우회를 하지 않는다.
- README를 역으로 읽어 지식 베이스를 채우지 않는다. 원래의 사용자 결정·근거 문서·구현 증거로 하네스·위키를 먼저 갱신한다.

## 검증

문서 변경은 링크, 정보 누락, README 근거 범위, 계획·구현 상태 구분, `git diff --check`를 확인한다. 코드 변경은 해당 PR의 검증 기준에 맞는 테스트를 수행한다. 실행하지 않은 검증을 완료했다고 기록하지 않는다.
