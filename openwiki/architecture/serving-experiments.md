# 서빙과 실험의 책임 분리

## 확인 범위

이 페이지는 세션에서 합의한 초기 방향을 설계 기록과 대조해 정리했다. **설계 합의를 확인한 것이며 구현 또는 실행 검증을 완료했다는 뜻이 아니다.** 현재 저장소에는 제품 Controller, CRD, 추론 서버 및 테스트 코드가 없다. 아래 이름은 예정된 API 이름이고 필드와 상태 스키마는 아직 정해지지 않았다.

## 해결하려는 문제

첫 실험은 Kubernetes에서 추론 서버를 축소하거나 교체할 때 진행 중인 스트리밍 응답이 어떤 조건에서 중단되는지 재현하는 것이다. 배포용 CRD 자체보다 재현 조건, 원인 분석, 수정 전후 검증이 목적이다. 특정 엔진에 결함이 있다고 전제하지 않는다.

운영 문제를 설명하려면 요청 중단율·완료율뿐 아니라 종료 소요 시간과 응답 지연을 함께 봐야 한다. 종료 대기 시간을 늘리는 변경은 요청 완료와 자원 회수 시간 사이의 영향을 함께 검증해야 한다. 아직 측정값이나 성공 임계값은 없다.

## 두 수명주기

| 구성 | 설계한 책임 | 수명주기 |
| --- | --- | --- |
| ModelServing | 모델·실행 이미지·자원·배포 설정을 표현하고 Deployment·Service 관리 | 서버의 원하는 상태를 지속적으로 유지 |
| ExperimentRun | 기존 서버를 참조해 부하와 종료·교체 실험을 조율하고 결과 판정 | 한 CR당 한 번의 실험 실행 |

서버 하나로 여러 실험을 수행할 수 있으므로 서버와 실험을 분리한다. 초기에는 두 Reconciler를 하나의 Operator 프로세스에서 실행할 방향이다. 별도 CR이 반드시 별도 Operator 배포를 의미하지는 않는다.

## 소유권과 변경 경계

실험은 대상 서버를 참조하며 소유하지 않는다. 실험 삭제로 기존 서버가 삭제되어서는 안 된다. 실험 Controller는 부하 발생 Job과 실험용 설정을 관리할 예정이며, 서빙 Deployment를 직접 변경하지 않는다.

서버 설정 변경은 ModelServing의 명시적인 인터페이스를 통해 요청하는 방향이다. 자동 확장과 실험의 수동 조작이 경쟁할 때의 정책은 미결정이다. 이 정책 없이 두 Controller가 동일한 필드를 관리하도록 구현해서는 안 된다.

## 실험 실행과 판정

예정된 흐름은 대상 준비 확인 → 부하 시작 → 요청 처리 중임을 확인 → 종료·교체 유발 → 기록 수집 → 결과 판정이다. 실험 Controller의 재시작·재조정으로 완료된 실험을 다시 실행하지 않도록 설계하며 재실험은 새 CR로 표현한다.

실험 절차가 정상 종료한 것과 성공 기준을 통과한 것은 다르다. 수집이 완료됐지만 스트리밍 중단이 발생했다면 실행은 완료됐어도 판정은 실패할 수 있다. 구체적인 상태 필드와 판정 정책은 아직 정의되지 않았다.

## 다음 설계에서 정할 부분

API 스키마, 대상 준비 대기와 실패 처리, 확장 설정과 실험 조작의 충돌 정책, 성공 임계값을 구체화해야 한다. 모델 레지스트리나 자체 스케줄러를 구현한 상태로 가정하지 않는다.
